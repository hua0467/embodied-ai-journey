# 同一个评估脚本，结论从 -32.6% 翻到 +37.8%：给机器人 VLA 模型做 LoRA 微调的一天

> **快速了解**
>
> 我是一名汽车服务工程专业的大四学生，在一家机器人初创公司做具身智能研发助理。公司把一台 48GB 显存的 RTX 4090 交到我手上负责。这篇文章记录我用 LoRA 给机器人视觉-语言-动作（VLA）模型 SmolVLA 做微调的一天：三策略对比选型 → LoRA 微调只训练 2.5% 参数 → 自采数据因网络不通改用公开遥操数据集做替身 → 评估时因为坐标系搞错得出完全相反的结论（-32.6%），修正后变成 +37.8%。
>
> 关键结论：LoRA 微调在 4090 上 8 分 42 秒完成 2000 步，微调后模型输出与真值动作的平均距离下降 37.8%；一天踩了 12 个坑，没有一个是算法问题。文末附完整技术笔记链接（命令、超参、踩坑全表）和汽车-机器人对照表。

## 一、先选型：三个策略，像挑三台性格不同的车

给机器人选策略模型，有点像挑车。

- **ACT**：皮实的面包车。5200 万参数，2000 步 1 分 22 秒，loss 1.266。不炫技，但链路验证、快速原型它最快。
- **Diffusion Policy**：性能轿跑。2.6 亿参数，2000 步 2 分 48 秒，loss 0.033。拟合精度最好，代价是重。
- **SmolVLA**：能听懂人话的智能座舱。总参数 4.5 亿（可训练 1 亿），2000 步 1 分 48 秒，loss 0.105。它天生吃语言指令——这是我负责的方向：VR 遥操采集的数据，每条都带一句人话指令。

三台车都试了一圈（同一份官方数据集、各 2000 步），我把方向定在 SmolVLA。但全参数微调一次要动 1 亿参数，checkpoint 一大坨。这时候 LoRA 就该上场了。

## 二、LoRA 微调：只换零件，不换整车

LoRA 的思路，用修车的话说就是：**发动机变速箱都不动，只加装一套小零件，让整车行为适配新路况。**

具体到模型：在原有权重旁边插入低秩适配器，只训练这部分。我的配置是 r=16、目标模块 all-linear，最终**可训练参数 1152 万，只占总参数 4.6 亿的 2.5%**。checkpoint 从全量模型的几百 MB 缩到 125MB——存 20 个"不同指令风格"的适配器，成本比存 20 个全量模型低一个数量级。

训练命令核心长这样（完整版在文末技术笔记里）：

```bash
python -u src/lerobot/scripts/lerobot_train.py \
    --policy.type=smolvla \
    --peft.method_type=lora \
    --peft.r=16 \
    --peft.target_modules=all-linear \
    --policy.pretrained_path=lerobot/smolvla_base \
    --policy.push_to_hub=false \
    --dataset.repo_id=~/lerobot_data/... \
    --dataset.video_backend=pyav \
    --batch_size=4 --steps=2000
```

在 4090 上，2000 步纯训练 8 分 42 秒，约 3.8 步/秒。

## 三、第一个坑：训练和"挂载旧零件"是两条路

第一次跑，我把 `--policy.use_peft=true` 也加上了——看起来顺理成章，"我要用 PEFT"嘛。

报错：`Can't find 'adapter_config.json' at 'lerobot/smolvla_base'`。

排查半天才读懂框架的语义：`use_peft=true` 的意思是"**加载一个已经训练好的 LoRA 适配器**"（推理场景），而训练时新建适配器走的是另一条路——只传 `--peft.method_type`、`--peft.r` 这些参数就行。两个参数看起来都在说同一件事，实际一个是"装新零件"，一个是"检查旧零件"。

删掉 `use_peft`，2 步冒烟验证通过，再放 2000 步。

## 四、数据没到位：两个网段之间没有路

傍晚准备换自己的数据，先查网络拓扑，结果：训练机在办公室 WiFi 网段，机器人自带路由器在另一个网段，两个网段之间没有路由互通，训练机有线网口是 DOWN 的，现场还没有网线。

数据在采集端电脑上，车到不了对面。迁移方案定了两个（改接机器人路由器 WiFi / U 盘），但都要等现场。

这时候有个选择：干等，还是先找替身数据把全流程跑通？我选了后者——用公开真实遥操数据集 `aloha_static_coffee`（50 个 episode、55000 帧、含语言指令）当替身。1.57GB，用镜像直链 + curl 并行下载，v3.0 格式验证通过，直接开训。

## 五、替身数据：驾校的考试车

替身数据上 LoRA 微调 2000 步：**loss 0.982 → 0.108，单调收敛，没有过拟合**（对比上午官方数据那次 loss 后期反弹到 0.846——小数据集步数要节制，这本身就是个教训）。

然后是评估。这次除了"微调前后输出差异"这种分布对比，我加了一个更硬的指标：**预测动作 vs 真值动作的距离**——取 20 个随机帧，让模型按数据集内指令预测动作，和人类演示的真值动作比 L2 距离。距离下降 = 输出更贴近演示。

## 六、评估翻盘事故：扭矩扳手的单位搞错了

首版结果跑出来：微调后距离**上升 32.6%**。

看到这个数我心里一沉——微调反而变差了？正准备把这个结论写进报告，顺手多查了一步：`predict_action_chunk` 输出的动作在**归一化空间**（训练时数据被标准化过），而真值动作在**原始动作空间**。两边根本不在一个坐标系。

这就像修车时拿扭矩扳手拧螺丝：**扳手显示的是 N·m，维修手册写的是 kgf·m。数字都对，结论全错。**

用 `meta/stats.json` 里的 mean/std 把模型输出反归一化到原始空间，重跑：**微调后距离下降 37.8%**。同一个脚本，同一个数据，结论从 -32.6% 翻到 +37.8%。

这是我今天收获最大的一课：评估方法学比模型本身更容易出错。以后任何"预测 vs 真值"的对比，先问一句——两边在不在同一个坐标系。

## 七、替身数据的价值边界

数字很好看，但有个诚实的注脚：aloha_static_coffee 属于 Open X-Embodiment 数据集，很可能就在 SmolVLA 的预训练语料里。也就是说，base 模型本来就会这个任务，37.8% 的改善是在"已知任务"上榨出来的。驾校的考试车练熟了，不代表开自己的车就顺——等自采 VR 数据到位后重跑，才能看到真正的微调收益。

但今天的价值不在 37.8% 本身，在于：**微调管线（数据验证 → LoRA 训练 → 双指标评估）在我手上完整跑通了**，数据一到，换一个 `--dataset.repo_id` 就能复用。

## 今日教训清单

| # | 教训 | 代价 |
|---|---|---|
| 1 | `use_peft=true` 是"加载已有适配器"，不是"新建 LoRA"，训练只传 `--peft.*` 参数 | 一次失败训练 + 半小时排查 |
| 2 | 新版 HF config 多了 `type` 字段，旧框架解析直接崩 | 评估脚本连崩两轮 |
| 3 | 模型 config 的图像键（camera1/2/3）与数据集键（observation.images.top）不一致，手动加载必须用数据集 features 覆盖 | 一次失败的评估运行 |
| 4 | 评估坐标系不统一：模型输出在归一化空间、真值在原始空间，直接比较结论完全翻盘 | 差点把 -32.6% 写进报告 |
| 5 | HF 库在镜像端点下有元数据回落 bug，绕开库直接 curl 反而最稳 | 下载反复失败半小时 |
| 6 | 小数据集（50 eps）2000 步会过拟合，loss 后期反弹 | 官方数据那次训练曲线不可用于汇报 |
| 7 | 网络排查要先画拓扑：训练机只有 WiFi、机器人是独立网段，两网段无路由 | 数据迁移卡住，只能等现场 |
