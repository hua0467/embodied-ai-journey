## 先交代一下这东西怎么来的

实习前几天我还在老老实实地学 Prompt Engineering、Agent 范式、RAG——一个工具一个工具地用。但很快就发现一个问题：单个 AI 对话做不了正经项目。你让它写个完整后台，它写到一半开始胡言乱语，因为上下文窗口炸了。

然后我想起第二天学的 Multi-Agent 协作——既然 Agent 可以分工，我为什么不能像分配任务一样给不同的 AI 分配不同的活？

试了两天，发现真的能行。下面就是目前为止沉淀下来的方法论。

---

## 为什么单靠一个 AI 搞不定正经项目

三个原因，全是踩坑踩出来的：

**第一，窗口会炸。** 一个完整项目涉及几十个文件、上百行业务逻辑。你塞越多，AI 忘越多。聊到后面它会忘记你开头说过的话——跟金鱼一样。

**第二，一个模型搞不定所有事。** Claude 写代码很强，但让它设计 UI？出来的东西像 2010 年的后台管理系统。v0 做前端页面很猛，你让它写后端逻辑？它不在那个赛道上。

**第三，没有人查你的作业。** 同一个模型生成代码，同一个模型审查 = 睁一只眼闭一只眼。盲区完美重叠。你高考的时候，出题人和阅卷人得是不同的人吧？AI 项目也一样。

## 换个思路：你不是在用 AI，你是在开 AI 外包公司

```
以前：我 ──问──→ [一个 AI] ──答──→ 我（祈祷答案是对的）

现在：
              ┌──→ [AI 研究员] ──→ 调研结论 ──┐
              │                                  │
我（甲方）──→ [AI 架构师] ──→ 技术方案 ──→ 我审核 ──→ [AI 前端]
              │                                  │         ├──→ [AI 后端]
              │                                  │         ├──→ [AI 测试]
              └──→ [AI 设计师] ──→ 视觉稿 ──→ 我审核    └──→ [AI 文档]
```

你的角色变了：从「写代码的人」变成了「管项目的人」。需求你来定、架构你来审、不同 AI 之间的上下文你来传。代码、设计、文档、测试——全是 AI 干，但你得告诉它们做什么、检查它们做对没有。

这跟汽车的总装厂逻辑一样：你不会自己去车每一个零件，你管供应链——谁供发动机、谁供变速箱、谁做质检。你定标准，别人执行。

## 我的 AI 工具分工表

这周试下来，目前觉得好用的搭配：

| 角色 | 我用什么 | 干什么活 |
|------|---------|---------|
| 架构师 | Claude | 拆需求、定方案、画架构图 |
| 研究员 | Perplexity | 搜竞品、查最新文档 |
| 后端 | Claude Code / Cursor | API、数据库、业务逻辑 |
| 前端 | v0（v0.dev） | 生成页面、组件、交互 |
| 设计师 | Midjourney | Logo、Banner、空状态图 |
| 测试 | Claude（新开对话） | 生成测试用例、做代码审查 |
| 文档 | Claude | API 文档、用户手册 |
| 部署 | Railway / Vercel | 点一下上线 |

**一个关键教训**：测试和代码审查一定要换一个对话窗口、或者干脆换一个模型。同一个 AI 生的代码，同一个 AI 查——查了个寂寞。

## 六个阶段，从零到上线

这是我现在用的流程。不一定对，但至少能跑通。

### 阶段 1：先把需求问清楚

不要一上来就让 AI 写代码。先把它当产品经理用。

我一般这样开场：
> "你现在是一个 B 端产品经理。我的场景是 [工业巡检机器狗的数据管理平台]。请像访谈客户一样分几轮问我问题，帮我搞清楚到底要做什么。"

问完几轮之后，把结论喂给 Perplexity 搜竞品。最后把需求和竞品分析一起喂给 Claude，让它出技术方案。

这一步产出的 PRD 和技术方案，**后面每一步都要重新贴给 AI**。不贴 = 白做。AI 没有记忆，每次都是新对话，你不在开头给它这段上下文，它就瞎猜。

### 阶段 2：让 AI 画页面

把 PRD 里的页面列表贴给 v0（v0.dev），让它生成前端页面。我会特别强调一句：「每个页面都要有 loading、empty、error 三种状态。」这条如果不加，AI 默认只给你完美数据状态下的页面——实际产品里 80% 的 bug 出在异常状态上。

然后找同事或朋友试用原型。这一步花的 10 分钟，能省掉后面 10 小时的返工。

### 阶段 3：写后端——最重要的一条教训

**不要让 AI 一次性生成所有代码。** 我第一次干这个事，给了一个巨长的 Prompt：「帮我做一个完整的后台系统，包含用户管理、设备管理、巡检记录、告警中心」。它确实生成了——一坨 3000 行的屎山，Bug 满天飞，而且没法定位问题在哪。

后来学乖了，一个一个模块来：
- 模块 1：用户注册登录 + JWT
- 模块 2：设备 CRUD
- 模块 3：巡检记录 + 分页筛选
- ...

每个模块写完了跑测试、调通了，再进入下一个。慢一点，但出来的东西能用。

### 阶段 4：前后端往一块拼

把后端的 Swagger 文档导出成 JSON，直接喂给 v0：「替掉所有 mock 数据，接上真实 API。」

遇到 Bug 时别慌——把前端发了什么、后端返回了什么、相关代码贴给 Claude，让它排查。90% 的情况它能直接定位。

### 阶段 5：上线

让 Claude 生成 Docker 配置 + 部署脚本。Railway 或 Vercel 上点 Deploy。部署完之后拿手机用 4G 访问一下生产环境——能走通就算过了。

### 阶段 6：补文档

代码写完了 ≠ 项目做完了。API 文档、用户手册、技术复盘——这三样让 Claude 帮你写。尤其是技术复盘，把项目的技术债务、安全漏洞、优化方向全列出来，这是你下次迭代的地图。

## 怎么保证质量不翻车

### 核心手段：换人审查

永远不要让同一个 AI 审查自己写的东西。新开一个对话，把内容贴进去：「你是一个资深 [后端/前端/安全] 工程师，严格审查以下内容。每个问题标严重程度。」

两个 AI 的盲区不一样，叠加之后能抓到大部分问题。这跟代码 review 的原理一模一样。

### 兜底手段：把自己当甲方

项目快收尾时，用这个 Prompt：

> "假设你是这个项目的甲方，明天验收付尾款。列出你会检查的 20 个点，然后逐项自测，给出通过/不通过/有条件通过。"

这招是我导师教我的——他说你永远会在甲方视角下发现新 Bug。试了一次，确实。

## 五条我自己试过的法则

1. **AI 干 80% 的活，但最关键的 20% 你干。** 需求判断、架构决策、上下文传递、最终验收——这些 AI 替不了你。你省下写代码的时间，应该花在「确认方向是对的」上。

2. **一个生成，另一个审查。** 成本最低的质量提升手段，没有之一。

3. **每次对话都贴 PRD。** 不贴 = AI 在盲猜你的需求。别偷这个懒。

4. **一小口一小口吃。** 「帮我做一个完整后台」= 屎山。「先做登录模块」→ 验证通过 → 「再做设备管理」= 能用的系统。

5. **先让它跑起来，再让它好看。** 第一版的目标是「能用」，不是「完美」。能用的东西可以迭代变好，完美的幻想永远做不完。

## 我踩过的坑

| 坑 | 怎么掉的 | 怎么爬出来的 |
|------|---------|------------|
| 一次性需求 | 「帮我做一整个系统」 | 拆成独立模块，逐个来 |
| 上下文丢失 | AI 写到后面忘了前面 | 关键信息每个对话都重新贴 |
| 直接上线 | 复制 AI 代码 → 部署 → 炸了 | 先在本地跑通再说 |
| 不贴背景 | 每次问都不给上下文 | PRD 摘要固定在每次开头 |
| 只用一个模型 | 啥都问 ChatGPT | 代码找 Claude，设计找 v0，调研找 Perplexity |
| 第一版就交付 | 觉得 AI 生成的就是成品 | 至少迭代 3 轮，每轮审查修复 |
| 忘记安全检查 | 代码能跑 → 上线 → 被人注入 | 上线前单独开一个对话做安全审查 |
