## 1. 链路通了：从手柄到关节

上一篇写的是 Quest 3 手部追踪 → PC 解 IK 的链路，机器人是不动的。这篇是真机——机器人真动，你在头盔里看到自己的虚拟手，机器人的臂跟着走。

这次用的是另一套方案：一体机（PICO 4）手柄遥操。手柄位姿 → APP 里解 IK → UDP 发 JSON → 机器人上的 ROS2 节点 → 关节指令 topic → 臂驱动器执行。四层，每层今天都活着。

```
VR 手柄（方向盘）
  → APP 解 IK（整车控制器：手位姿 → 14 个关节角）
  → UDP JSON（CAN 总线：带 safety 字段）
  → ROS2 节点 → 关节指令 topic
  → 臂驱动器（执行器）→ F1 双臂 14 关节真动
      ▲
      └─ 关节角回读（编码器，就像轮速传感器）
```

这套东西和线控底盘几乎一一对应。车上你打方向盘车轮就转；这里你手往哪伸，机器人的臂就往哪伸。区别是：车没有 14 个关节，也不会在跟踪丢失的时候把自己拧起来。

链路的"绿旗信号"只有一条：日志里出现 `Safety check passed, robot can execute`。出现，机器人必动；不出现，必不动。没有例外。

## 2. 安全状态机三件套

上午最大的认知反转：机器人不动，我查了半小时代码和网络，最后发现是**安全设计在工作**。

APP 发的每个 UDP 包都带一个 `safety` 字段，机器人上的节点照单执行。三个状态，日志里出现哪个就对照哪个：

| 日志里的 reason | 含义 | 处理 |
|---|---|---|
| `teleop_disarmed` | 未使能 | 按「使能」按钮 |
| `calibration_required` | 手柄标定未完成 | 手柄静止 2~3 秒，自动清除 |
| `session_not_focused` | 摘了头盔 / APP 在后台 | 戴头盔、切回前台 |

第三个最坑。我为了看电脑上的日志，反复摘头盔——摘一次，机器人停一次。我还以为是链路坏了，其实是链路在工作：就像有些车检测到驾驶员离座会自动挂 P 挡，你骂车不走，其实车在保护你。

这事的价值不在技术本身，在于认知：**一个系统"不动"，先查它的安全逻辑，再查它的功能逻辑。** 功能坏了和安全在工作，修法完全相反。

## 3. 录制数据：相机和关节怎么同步

链路通了就开始录。每帧 = 14 个关节角（rad）+ 一张机载相机的 JPEG，同步存进 HDF5。今天录了 ~1500 帧。

两个和想象不一样的事实：

**第一，实际帧率 7~9Hz，不是 50。** 录制脚本的 `--fps 50` 只是上限，真实帧率取决于 APP 的发送速率。慢，但真实。低帧率对训练的影响还没评估，先把数字如实记下来。

**第二，数据格式的细节都是踩出来的。** `action[i] = state[i+1]`（动作是下一帧的状态）；未受控的臂存 NaN 而不是 0——0 是假的，NaN 才是"这侧没数据"。每 1000 帧自动落盘一次兜底，进程被强杀最多丢最后 999 帧。

录制的坑：

- 相机打不开 = 推流服务占着设备。录数据和 RTSP 推流互斥，录制前必须先停服务
- 相机线重插后设备号从 video27 漂到 video0~7。挨个节点试了才知道 video6 是彩色流，video0/2/4 是深度和红外（协商不了 JPEG），video1/3/5/7 是元数据节点（根本不是采集设备）

## 4. 构型失控：臂怎么拧的

下午，左臂把自己拧成了艺术造型。事故链很短：

```
手柄出了可视区 → 光学跟踪丢失 → IK 拿到跳变的手位姿
→ 关节指令跳变 → 臂拧了
```

说人话：传感器瞎了一瞬间，车自己打了把方向盘。

应急五步（用血换的，已写进操作手册）：

1. **Ctrl+C 停录制**——这轮数据作废，别混进数据集
2. **杀遥操进程**——掐断命令流，臂冻结
3. **摘头盔 + 关使能**——双保险
4. **读关节角**——定位问题关节
5. **用现成的回零工具归位**

两个当场纠错，比事故本身更有价值：

- 我第一反应是写一个 30 秒正弦插值的回零脚本。带我的师兄早写好了单关节调试工具，一个按键回零。我的脚本删了。**动手写新东西之前，先把现有的工具全部读一遍。**
- 我说"肘关节折了"，被纠正——臂是自然垂着的，只是掌心朝外。这个纠正直接改变了诊断方向：不是机械卡死，是**编码器读数与真实位置对不上**。物理姿态描述错一个字，排查方向就歪一百八十度。

事后把应急流程写进手册时，我意识到真实的第一反应其实不是 Ctrl+C，是先拍照发群。手册里第一条还是写 Ctrl+C——因为手册是给你冷静时读的。别问我是怎么知道的。

## 5. J3 排查：从读数冻结到硬件判定

回零后 13 个关节都归零了，只有左臂 J3 停在 2.8407 rad（约 163°），而臂物理上垂直朝下。

汽车类比：仪表盘显示车速 163，车稳稳停着——你不会修发动机，你会怀疑轮速传感器。J3 编码器就是这么被钉死的。

| 时刻 | 事件 | J3 读数 (rad) | 结论 |
|---|---|---|---|
| 回零后 | 13 关节归零，J3 不动 | 2.8407（bit 级冻结） | 疑似编码器死亡 |
| 直接发关节指令 | 臂无响应，读数一字不差 | 2.8406572341918945 | 命令链路没问题 |
| 数分钟后 | 读数**自己**变了 | 2.7266 | 编码器还活着 |
| 连续采样 6 次 | 读数稳定 | 2.7556 | 不是抖动，是漂移 |
| 软件标零（把当前位置设为软件零位） | 服务返回成功 | 2.87（还在爬） | 软件层拿它没办法 |

排查是分层排除法：APP → 网络 → 节点 → 命令链路 → 编码器本身。每排除一层，就往硬件逼近一层。最后两个证据把结论钉死：**读数自行漂移**（这是机械特征，软件产生不了）+ **软件标零无效**（软件层无解，只有硬件能解释）。

顺便说个容易踩的语义坑：驱动服务的"软件标零"是把**当前位置**设为软件零位，不是"回到零位"。拧着的时候调它，异常姿态就成了新零位，更乱。我在手册里把这句加粗了。

最后定了一条红线：**编码器读数异常时，该臂禁发任何命令**——驱动器是瞎的，它以为臂在 A 位置，其实在 B 位置，你发的命令它可能往反方向猛推。修复前，左臂不参与遥操。

诚实交代进度：到这里，正式数据集还一帧都没录。今天跑通的是链路和录制，卡住的是硬件。

## 6. 断电复位实验：明天见分晓

收工前做了一个实验：关机 → 所有关节失力 → 手动把每个关节摆回正常位置。物理姿势对了，但编码器这道题还没交卷。

明天开机第一件事是读 J3，然后对号入座：

| 明天 J3 的表现 | 结论 |
|---|---|
| 读数回到 ~0 且与物理姿态吻合 | 驱动侧累计误差，断电复位有效 |
| 读数还是错值 | 硬件实锤，返修 |

就算读数对了，还要过三道安全闸才解禁左臂：读数吻合 → 60 秒稳定性检查（读数不爬）→ 微动测试（小角度动一动，回读跟手）。任何一道不过，都算没过。

实验结果明天更新在这篇文章里。这是"进行时"的代价——故事没有结尾，因为事情还没发生。
