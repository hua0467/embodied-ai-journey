## 先搞清楚 π₀.₅ 是个什么东西

π₀.₅（读作 pi-zero-point-five）是 Physical Intelligence 这家公司开源的一个具身大模型。你可以把它理解成一个「机器人基础模型」——就跟 GPT 是文本的基础模型一样，π₀.₅ 是给机器人用的。

它的架构特别有意思：**一个 3B 的视觉模型（PaliGemma）当眼睛，一个 300M 的动作模型（Gemma）当小脑。** 眼睛负责看图，小脑负责算动作。加起来大概 4B 参数。这个方法叫 Flow Matching，你不用深究，把它理解成「从当前状态平滑过渡到目标状态」就行。

关键点是：π₀.₅ 开箱就能用，但你需要**用自己的机器人数据做后训练**，让它适应你的机器人。就和你在预训练模型上做微调一个道理。

然后问题就来了：它要什么格式的数据？

---

## LeRobot：具身智能数据集的"国际标准"

π₀.₅ 只认一种数据格式，叫 LeRobot（HuggingFace 搞的）。现在最新版是 v3.0。一个 LeRobot 数据集的目录长这样：

```
your_dataset/
├── meta/
│   ├── info.json          ← 数据集的"说明书"
│   ├── episodes.jsonl     ← 每条演示的起止和标签
│   ├── tasks.jsonl        ← 任务文本（"拿起方块"之类）
│   └── stats.json         ← 归一化统计量（训练前算出来的）
├── data/
│   └── chunk-000/
│       ├── episode_000000.parquet   ← 真正的数据在这里
│       └── episode_000001.parquet
└── videos/                 ← 摄像头录像（有的话）
```

有人可能会问：Parquet 是什么？就是个表格文件，跟 Excel 差不多，但是专门给大规模数据设计的，读写快、压缩好。每行是一帧，每列是一种数据。

## 八个必须字段——少一个训练就报错

每行 Parquet 必须包含这 8 列：

| 列名 | 存什么 | 举个例子 |
|------|--------|----------|
| `observation.state` | 机器人当前关节角度 | `[0.5, -0.3, 0.1, 0.8, 0.0, -0.4]`（6 个关节） |
| `action` | 目标关节角度（你要让机器人去哪） | `[0.52, -0.28, 0.12, 0.79, 0.0, -0.38]` |
| `timestamp` | 这一帧的时间戳 | `3.24`（第 3.24 秒） |
| `episode_index` | 第几条演示 | `0`（第一条） |
| `index` | 全局帧编号 | `142`（第 142 帧） |
| `task_index` | 任务编号 | `0`（第一个任务） |
| `next.done` | 是不是最后一帧 | `True` / `False` |
| `next.reward` | 成功=1，失败=0 | `1.0` 或 `0.0` |

**我踩过的坑**：`info.json` 里有个 `features` 字典，必须写清楚每列的 `dtype` 和 `shape`。LeRobot 老版本不需要这个，v3.0 强制要求，少了就直接 KeyError。我当时对照 GitHub issue 查了半个小时才发现。

## 数据管线的四层转换——理解这个就不怕报错了

你把数据扔进去，openpi 内部会过四道工序。你不用自己实现，但必须理解每一步在干什么，否则出错了你都不知道从哪查：

```
原始 Parquet
   │
   ▼
第一层：RepackTransform（换名字）
   │  把不同机器人的列名统一成内部格式
   │  比如你的 "observation.state" → 内部叫 "state"
   │  你的 "action" → 内部叫 "actions"
   │
   ▼
第二层：DataTransform（算动作模式）
   │  决定用绝对动作还是相对动作
   │  绝对 = "关节 1 转到 0.5 rad"
   │  相对 = "关节 1 在当前基础上 +0.02 rad"
   │  F1 场景建议用绝对，简单直接
   │
   ▼
第三层：ModelTransform（统一尺寸）
   │  图像 resize 到固定分辨率
   │  状态/动作向量 padding 到 32 维（F1 只有 6 个关节，后面自动补 0）
   │
   ▼
第四层：Normalization（归一化）
   │  把数据缩放到模型好消化范围
   │  π₀.₅ 默认用分位数归一化，不是 Z-Score
```

我拿汽车类比一下你就懂了：

- RepackTransform = 把不同供应商的零件统一编号（博世的喷油嘴叫「fuel_injector」，电装的叫「injector_fuel」，统一成一个名）
- DataTransform = 决定用绝对位置还是位移量控制节气门
- ModelTransform = 把接口尺寸统一（不匹配的加垫片）
- Normalization = ECU 的 MAP 图——把传感器电压映射到标准的 0-5V 范围

## 分位数归一化：为什么不用 Z-Score？

传统机器学习习惯用 Z-Score：减均值除以标准差。π₀.₅ 不这么干，它用**分位数归一化**。

公式很简单：`(x - q01) / (q99 - q01)`

q01 是第 1% 分位数的值，q99 是第 99% 分位数的值。相当于掐头去尾取中间 98% 的数据范围。为什么这么干？因为机器人关节数据经常有异常值——某个关节突然卡了一下、VR 追踪丢了一帧——Z-Score 对异常值很敏感，一个离谱的值能把整个标准差拉飞。分位数天生抗干扰。

**做数据采集的人要注意**：录完数据后必须跑一次 `compute_norm_stats.py`，算出 q01/q99 存到 `stats.json`。训练的时候模型会自动读取这个文件做归一化。不跑这步，训练启动时报错。

## 训练就一行命令——前提是前面都对了

```bash
lerobot-train \
    --dataset.repo_id=你的数据集名称 \
    --policy.type=pi05 \
    --policy.pretrained_path=lerobot/pi05_base \
    --output_dir=./outputs/training \
    --batch_size=32
```

但这一行命令能跑通的前提是：

1. ✅ Parquet 文件名和路径对
2. ✅ 8 个必须列都在，dtype 和 shape 对
3. ✅ info.json 的 features 字典写全了
4. ✅ episodes.jsonl 里每条 episode 的起止正确
5. ✅ stats.json 已经算出来
6. ✅ 状态维度和动作维度跟配置一致

**六个条件缺一个，训练就会在一个你意想不到的地方报错。** 而且报错信息通常不友好——不是「features 字典缺了 observation.state」，而是深层的 KeyError 或者 shape mismatch，让你对着报错信息怀疑人生。

## 跟我这个项目的对应关系

我在搭的管线是：Quest 3 VR 手部追踪 → IK 解算 → F1 机器人关节指令 → 录数据 → 转 LeRobot → 喂给 π₀.₅。

作为数据采集的人，我只需关注三件事：

1. **列名不能写错。** `observation.state` 不是 `observations.state`，不是 `state`，多一个字母少一个字母都不行。
2. **状态和动作的维度要对。** F1 是 6 个关节 + 1 个夹爪 = 7 维。录数据的时候每一帧的状态和动作都必须是 7 维的 float32 数组，不能多不能少。
3. **录完第一件事是跑归一化统计。** 不要等到训练的时候才发现没算 stats。

## 写到最后的感受

研究完 openpi 的数据格式之后有一个很深的感触：**做数据的人在 AI 时代被严重低估了。**

模型架构是别人写好的、权重是别人训练好的，你只是在做后训练。但决定后训练效果的最关键因素，不是模型，是你的数据质量。你的数据标注方式、数据组织形式、归一化方式——每一个细节都会直接决定模型的输出是「精准地抓起方块」还是「精准地把方块推下桌子」。

做数据的不是工具人。我们造的是模型的教科书。教科书写错了，再好的学生也学不出正确答案。

另外一件事：我们这个项目有三个人在做不同的采集方案（我走 VR+真机、学驰走 EGO+无实体、蔚祺走仿真+URDF），但最后数据汇到同一个 LeRobot 格式、同一个 π₀.₅、同一个 Isaac Sim 训练管线。如果我这边格式搞错了，影响的不是我自己，是三个人的活全白干。反过来说，我把格式规范吃透了，另外两个人也能直接用——这就是数据管线在 VLA 项目里的位置：**承上启下，一头接采集，一头接训练。**
