> *被问太多次了。我的标准回答：这有啥的，做啥没区别，我大学专业课也没怎么听。*

## 我是谁

我叫 keywashion，一个正在跟自己的大学成绩单和解的人。

汽车工程专业，大三。如果大学有「出勤率反向排名」，我应该能进前十。高数挂过——不是学不会，是当时压根没翻开过课本。线代？我看到矩阵就想起高考数学最后一题的绝望感。专业课倒是去了几次，主要是考前那周。

但我有一个不谦虚的优点：**给我一个东西，我能从底层把它拆明白。** 不是为了考试，纯粹是手痒。小时候拆遥控车，大学拆发动机模型，现在拆 AI 系统。每个零件为什么在那、这条线为什么接这里、这个传感器信号走的是 CAN 还是 LIN——这些问题能让我凌晨三点还不困。

成绩单不反映这个能力。老师给的评价倒挺统一：「那小子脑子灵光，就是坐不住。」奇怪的是，我明明是缺勤率最高的那个，但每个老师都记得我。可能上课不去还能被记住，本身就是一种能力。

三个月前我连「大模型」和「大数据」都分不清。「具身智能」？听起来像某种瑜伽流派。

然后误打误撞进了一家做工业巡检机器狗的创业公司。岗位：具身智能研发助理。第一天报到的时候我还在想：他们是不是招错人了。

现在看来，也许没有。

这个仓库记录了我从零开始学的东西。一个非典型学生，一条没人带的路，一堆自己琢磨出来的理解。写得比较野，不保证对，但保证是真的。

## 为什么一个学汽车的要搞机器人

这个问题我想了很久。真正想通是在入职的前一个月，学校正好有一个课前五分钟的分享汇报，我就分享了我实习的选择原因吧
我的大致理解就是(也不知道对不对）:

汽车工程的骨架：**传感器 → ECU 决策 → 执行器 → 反馈 → 修正**。一套闭环。

具身智能的骨架：**摄像头/LiDAR → 算法决策 → 电机 → 新数据回传 → 调整**。也是一套闭环。

PID 控制、查表标定、CAN 总线、多传感器融合——这些我在大学里打瞌睡听进去的东西，换个领域居然全对上了。汽车里烧的是汽油，耗的是电，机器人里跑的是矩阵乘法，但控制逻辑没变。

> 找到这个对应关系之后，学习速度快了很多。因为你发现 80% 的「新知识」，其实是你已经会的东西换了件马甲。

## 第一周


### Day 1：遛了只铁狗

入职第一天，导师没让我看文档。他打开一个网页后台，把地址发给我：「去，遛一圈。」

不是什么高科技遥控器——就是一个浏览器里跑的 Web 控制台。左边是扫描后的地图，右边一堆参数面板，右下一个前后左右下蹲加速减速的按键。像玩网页小游戏。这一个系统是一个很牛的工程师写的，全技术栈都会连我的导师都在夸

我操作的那个机器狗只有一串编号，没有名字。四条腿，房不算大，它自己转了一圈，自己建了张地图，自己找了条路走。遇到障碍物自动绕开。

我当时脑子里两件事同时在转：
- 「卧槽这东西比我家的车聪明」
- 「这背后的逻辑我好像能懂」

后来回去查了资料才搞明白——它跑的是 SLAM（同时定位与建图），路径规划用的是 A* 变体，步态控制底层是 MPC。每一样拎出来拆解，都能在汽车底盘控制里找到一个对应的表亲。横摆角速度换成了步态相位，ESP 换成了力控，仅此而已。

那天回家路上一直在想：如果我大学认真学了线代，现在看 SLAM 的协方差矩阵应该不会一脸懵逼吧。算了，现在补也来得及。


### Day 2：发现大模型和 ECU 是一个妈生的

第二天开始啃 Prompt Engineering。本来以为会学到一堆「怎么写提示词」的技巧清单，结果我被一个底层事实震住了。

ECU 是怎么工作的？传感器给信号 → 在标定好的 MAP 图里查表 → 输出喷油量 → 氧传感器反馈 → 修正下次输出。

大模型是怎么工作的？你给 Prompt → 在训练好的概率空间里采样 → 输出 Token → CoT 自我修正。

**一模一样。**

甚至它们的「病」也一样：如果你给 ECU 一个坏的氧传感器信号，它会照 MAP 图喷出完全错误的油量——这不就是 LLM 的幻觉吗？输入信号错了，后面全偏，但它不会告诉你「我不确定」，它只会自信地输出一个错误答案。

所以 Prompt Engineering 本质上不是什么魔法——它就是**给一个没有眼睛的 ECU 提供最准确的传感器信号**。你描述得越清楚，它输出得越准。标定工程师干的就是这个活。

当天还过了一遍 Agent 的四种设计范式——Reflection（反思纠错）、Tool Use（调用外部工具）、Planning（先计划后执行）、Multi-Agent（多个 Agent 分工协作）。我脑子里自动翻译成了：闭环修正、调用子程序、路径规划、多 ECU 协同通信。大学里唯一没白学的就是控制理论。


### Day 3：RAG 就是开卷考试

第三天学 RAG。一句话就能说明白：大模型训练完那一刻知识就冻结了，RAG 是在它回答问题之前，先去知识库里现翻资料，塞进 Prompt，让它照着说。

不用 RAG = 闭卷考试。你凭记忆答。忘了？现编一个看着像的答案。这就是幻觉。

用 RAG = 开卷考试。给你一本书，你先查再答，准确率直接上天。

但 RAG 真正的脏活不在概念——在数据处理。PDF、Word、表格、图片、邮件……公司的文档格式五花八门，你得把它们全拆成统一的 JSON，切成大小合适的块，保证每一块都是一个完整的语义单元。切太大检索不准，切太小语义不全。

这个活占了 RAG 项目 80% 的时间。我把它类比成汽车装配线上的零件分拣：不同供应商的零件，得统一编码、分组、入库。你把活塞环和雨刮器螺丝分到同一个盒子里，装配的时候永远找不到。

学完这天我产生了一个想法：如果把公司机器狗的操作手册、巡检日志、故障记录全做成一个 RAG 知识库，新人来了直接问 AI 就行，不用追着老员工屁股后面问。这个想法我跟导师提了，他说可以试试。后续更新会放在这个仓库里。


### Day 4：不学了，先建个仓库把自己装进去

第四天没看新技术。花了一整天搞 GitHub——建仓库、配 Git、传文件、解决合并冲突（这个最搞心态）。把前三天的笔记整理好，内部日志扔进私有仓库，脱敏版放公开仓库。

搞完之后突然意识到一件事：以前我一直觉得「学完了再做」，但这四天的经验是——**先把你现在有的东西推上去，再慢慢迭代。** 第一天写的东西可能很糙，但至少它在，别人能看到。一个存在但不完美的仓库，比一个完美但从未创建的仓库有用一万倍。

这也是我接下来在这个仓库要做的事：持续更新，不怕糙，就怕没动静。


## 我目前的学习方法

试用四天，亲测有效：

**别读完再动手。** 看了两篇文章之后就去搭东西，哪怕是个垃圾 demo。一个跑起来的垃圾比一个完美的计划有价值。我在第三天差点犯这个错——想把 RAG 全部理论学完再写代码，被导师一句「你先跑一个看看效果」拉回来了。

**每学一个概念，在旧领域找对应物。** Prompt ↔ ECU 查表，CoT ↔ 逐级升档，Multi-Agent ↔ CAN 总线。找不到对应物等于你没真懂。

**不管学了什么，当天写下来。** 用自己的话写，不许抄原文。写不出来就是没学会。这个仓库里的东西全是这样憋出来的——有些写得还行，有些回头看想删，但不管怎样，它们都在。
